# Automating metadata-portal signing — feasibility & migration plan

## Context

Today, every runtime upgrade on a chain in `config.toml` triggers a manual ritual: the hourly GitHub Action (`.github/workflows/update.yml`) opens a draft PR with unsigned QRs, then a release manager must locally run `make signer`, scan each unsigned QR with a Polkadot Vault device that holds Parity's metadata-signing sr25519 key (`c46a22b9…`), scan the resulting signature QR back through their webcam, and push signed QRs to the PR. Runtime upgrades have become frequent enough that this is a real bottleneck.

The user (a Parity engineer maintaining this portal) wants to know whether this can be moved into CI, in light of [RFC-0078 "Merkleized Metadata"](https://polkadot-fellows.github.io/RFCs/approved/0078-merkleized-metadata.html), which fundamentally changes the trust model: when a chain has the `CheckMetadataHash` signed extension enabled, transaction signatures cryptographically commit to a specific metadata digest, so the offline signer no longer has to *trust* its metadata source — wrong metadata = invalid transaction at the runtime.

## TL;DR — answer to "can we do it?"

**Not by putting Parity's key in CI.** That key is the only thing protecting every Polkadot Vault user from a poisoned metadata feed; CI write access ≠ ecosystem-trust authority.

**Yes by leveraging RFC-0078**, *conditional on three preconditions*:

1. ✅ **Verified 2026-04-28** — every chain in `config.toml` has `CheckMetadataHash` live in its runtime metadata (queried via `state_getMetadata` over HTTPS; SCALE-encoded `CheckMetadataHash` ASCII present in the signed-extension list of all 18 chains: Polkadot, Kusama, Westend relays + every parachain currently configured).
2. ⚠️ **Unverified** — that Polkadot Vault v7.0+ accepts unsigned/un-pre-trusted metadata when the chain has the extension (vs. still requiring a verifier-signed metadata QR for display purposes). This is the load-bearing assumption that needs confirmation before Phase 1 ships.
3. ⚠️ **Adoption-dependent** — pre-v7 Vault users on these chains still need the legacy flow until they upgrade.

If P2 holds, the manual signing step disappears entirely — the portal becomes a metadata-distribution service, not a trust anchor. The work is real (compute the digest, change publication format, update the frontend, communicate the migration) but it is *not* a security regression — it just moves the trust root to the runtime, where RFC-0078 says it belongs.

## Current state (grounded)

- Unsigned QR generated by `cli/src/updater/generate.rs:18-37` (`generate_metadata_qr`) via `parity-signer`'s `generate_message::full_run` with `Sufficient { sufficient_hex: None, … }`.
- Manual signing in `cli/src/signer/mod.rs`:
  - `mod.rs:52` — `qr_reader_pc::run_with_camera` reads the signature QR off the Vault screen via OpenCV.
  - `mod.rs:98,109` — the scanned signature is passed as `sufficient_hex` into `full_run` to assemble the signed APNG.
  - The webcam path is the *only* signing input the CLI accepts; there is no file/HSM/CLI alternative.
- Verification at `cli/src/verifier/qr.rs:57-68` — embedded verifier public key must equal `config.toml`'s `verifier.public_key`.
- Algorithm is sr25519 by default; `is_ethereum(chain.name)` switches to `Encryption::Ethereum` (`cli/src/signer/mod.rs:82-85`).
- The signing key never leaves the Polkadot Vault device — that's the whole point of the air-gap. There is no "alternative authorized signer" path in the parity-signer fork pinned at `cli/Cargo.toml:22-26` (`novasamatech/parity-signer` rev `263b6641…`).

## Why CI-side automation of the existing flow is the wrong answer

If we put any sr25519 key into GitHub Actions (or AWS KMS, or a YubiKey-bot, or a sigstore-style ephemeral key) such that CI can produce QRs the Vault trusts, then:

- **Every Polkadot Vault user trusting `c46a22b9…` becomes vulnerable to whoever can write to this repo or its CI secrets.** That is a far weaker threat model than "physical possession of an air-gapped device."
- Key rotation requires every Vault user to re-import the new verifier — there is no good rotation story.
- Sigstore / OIDC / KMS approaches are improvements on raw secrets but do not change the underlying trust delegation: GitHub becomes the root.

We should not ship Option A under any framing. Acknowledge it briefly in the migration doc and move on.

## RFC-0078 path (what actually changes)

What RFC-0078 introduces:

- A canonical BLAKE3 Merkle tree over chain metadata; the root digest is baked into the runtime WASM at build time.
- The `CheckMetadataHash` signed extension binds every signed transaction to this digest — at the runtime, signatures are rejected if the digest the signer committed to ≠ the runtime's baked digest.
- The `merkleized-metadata` crate (v0.5.0 on crates.io, [docs.rs](https://docs.rs/merkleized-metadata/latest/merkleized_metadata/)) is the canonical Rust producer of digests and proofs from a runtime WASM.
- Polkadot Vault v7.0+ ([Nova Wallet docs](https://docs.novawallet.io/nova-wallet-wiki/wallet-management/hardware-wallets/polkadot-vault/metadata-less-signing)) supports "metadata-less signing": the wallet hands Vault a transaction QR that already includes the merkle proofs for the types needed to decode that specific transaction. Vault decodes, signs, includes the digest via `CheckMetadataHash`. Wrong proofs → invalid signature.

In the steady state of "all our chains have `CheckMetadataHash` + everyone is on Vault v7+":

- **The portal does not need to publish signed metadata QRs at all.** Wallets feed Vault per-transaction proofs at sign time; the portal becomes (at most) a way to publish the metadata + digest hash so that anyone (a wallet, a watcher, a downstream tool) can verify or reproduce.
- The release-manager ritual is gone. Metadata updates are pure data flow, no human signature needed.

## Preconditions still to verify (Phase 0)

**P1 — `CheckMetadataHash` is live in the runtimes we serve.** ✅ **DONE 2026-04-28.** All 18 chains currently in `config.toml` have the extension enabled in their live runtime metadata, verified by querying each `state_getMetadata` over HTTPS and grepping for the SCALE-encoded ASCII `CheckMetadataHash` (hex `436865636b4d6574616461746148617368`):

```

westend                 PRESENT     statemint-AH            PRESENT
bridge-hub-polkadot     PRESENT     collectives-polkadot    PRESENT
coretime-polkadot       PRESENT     people-polkadot         PRESENT
statemine-AH            PRESENT     bridge-hub-kusama       PRESENT
coretime-kusama         PRESENT     encointer-parachain     PRESENT

bridge-hub-westend      PRESENT     collectives-westend     PRESENT
coretime-westend        PRESENT     people-westend          PRESENT
```

A re-verification step belongs in the CI flow (a no-op `cargo run --release -- update --source node --check-metadata-hash` style assertion) so we get a loud failure if a chain ever rolls back. Folding this into the existing `update.yml` is one extra step.

**P2 — Polkadot Vault's authentication model for received metadata in the v7+ era.** ⚠️ Unverified. Public docs ([Nova Wallet metadata-less signing](https://docs.novawallet.io/nova-wallet-wiki/wallet-management/hardware-wallets/polkadot-vault/metadata-less-signing)) describe Vault v7+ accepting per-transaction merkle proofs from the wallet, but do not state whether the *bulk* metadata-update flow this portal serves still requires a verifier-signed payload for the Vault to display rich UI for non-RFC-0078 transactions. Two ways to resolve:

- **Empirical test** on a Vault v7.x device: try a Kusama transaction signed with metadata-less mode; separately try importing un-pre-signed metadata from a portal-style source. Document what works and what doesn't.
- **Ask the Polkadot Vault maintainers** (novasamatech / parity-signer fork owners) directly — this is one Slack/issue thread for an internal Parity engineer.

This question gates whether Phase 1 can fully replace the manual signing step, or whether modern-mode chains still need a Vault-signed payload for legacy display purposes.

**P3 — Vault adoption.** ⚠️ Need a number from the Vault team. If a meaningful tail of users is still on pre-v7 builds, we keep the legacy signed-QR flow working in parallel rather than deleting it. Recommended action item: open an issue on `novasamatech/parity-signer` asking about the v7+ rollout curve, plus add a deprecation-horizon banner on the portal frontend communicating the planned cutover.

## Recommended phased migration

### Phase 0 — close the remaining unknowns (1–2 days, mostly investigation)

- ✅ P1 done (above). Add a CI-time assertion that re-verifies the extension is present for every configured chain, so a future chain that rolls back the runtime upgrade is caught loudly rather than silently breaking modern-mode users.
- Pin down P2 with the Vault team in writing (test on a real device + issue/Slack to the maintainers).
- Get a P3 adoption number; decide a deprecation horizon for pre-v7 Vault users.

### Phase 1 — pilot on one chain end-to-end (recommended: Kusama relay)

Pick Kusama relay specifically because it has had the extension longest in the runtime source (`polkadot-fellows/runtimes/relay/kusama/src/lib.rs`) and ecosystem tooling (Nova Wallet, Talisman) is most likely to have been exercised against it. We do *not* delete the signed-QR flow yet — the portal serves both modes side by side, switched per chain via a `mode` field.

Concrete changes (Phase 1):

1. **`cli/Cargo.toml`** — add `merkleized-metadata = "0.5"` (line ~41, alongside other deps). The crate's `generate_metadata_digest(metadata, extra_info) -> [u8; 32]` is the single entry point we need.

2. **New module `cli/src/digest/mod.rs`** — thin wrapper:
   - `pub(crate) fn metadata_digest(meta_values: &MetaValues, specs: &NetworkSpecs) -> Result<[u8; 32]>` — wraps `merkleized_metadata::generate_metadata_digest`, plumbing in the spec_version, spec_name, base58 prefix, decimals, token_unit from `specs`. Reuse the existing `MetaValues` already produced by `cli/src/updater/wasm.rs::meta_values_from_wasm_bytes` and `RpcFetcher::fetch_metadata`.
   - One unit test that hashes a fixture WASM (committed under `cli/src/digest/for_tests/`) and asserts the digest equals a hard-coded reference value computed by an independent tool ([`polkadart` CLI](https://polkadart.dev/guides/use-metadata-hash/) or the runtime's own baked `RUNTIME_METADATA_HASH` from a known release).
   - Wire in `mod digest;` at `cli/src/main.rs:1-15`.

3. **`cli/src/config.rs`** — add `pub(crate) mode: ChainMode` to `Chain` (line 108-121), defaulting to `Legacy` for backwards compat:

   ```rust
   #[derive(Clone, Serialize, Deserialize, Debug, Default)]
   #[serde(rename_all = "lowercase")]
   pub(crate) enum ChainMode {
       #[default]
       Legacy,   // continue producing signed metadata QR
       Modern,   // RFC-0078 — publish digest only, no signed QR
   }
   ```

   In `config.toml`, add `mode = "modern"` to the Kusama entry only for Phase 1.

4. **`cli/src/export.rs`** — extend `ExportChainSpec` with `metadata_hash: Option<String>` and `mode: ChainMode`. Mirror in `src/scheme.ts:1-15` (`ChainSpec`).

5. **`cli/src/collector/export.rs`** — in `export_specs` (line 16-78), compute the digest for `Modern` chains using the new `digest::metadata_digest`. Skip the `metadata_qrs` / `specs_qr` lookups for modern chains (no QRs to publish). Populate `metadata_hash`.

6. **`cli/src/updater/mod.rs`** — for modern chains, skip `generate_metadata_qr` / `generate_spec_qr` calls (line 26-58). The `update` subcommand becomes a no-op for modern chains beyond updating the digest, which the collector handles.

7. **`cli/src/signer/mod.rs::sign`** — filter out modern-mode chains from `files_to_sign` so `make signer` doesn't try to sign nothing for Kusama. Already partially handled by `files_to_keep` in `cli/src/file.rs`, but worth a defensive check.

8. **`cli/src/verifier/`** — for modern chains, replace the signed-QR public-key check with: re-compute the digest from the runtime WASM and assert it matches the value in `data.json` (so a CI-side typo / corruption is caught). This is the CI-time P1 re-verification mentioned in Phase 0.

9. **Frontend** (`src/components/Network.tsx` plus a new `src/components/MetadataHash.tsx`):
   - When `spec.mode === "modern"`, render the digest hex + a short explainer ("This chain uses RFC-0078 merkleized metadata. Polkadot Vault v7+ verifies metadata against this digest automatically — no signed QR is required. [link to RFC]").
   - Hide the "Add to Signer" call-to-action for modern chains; show a small banner on legacy chains instead noting the planned migration.
   - `src/scheme.ts` mirrors the new fields.

10. **`.github/workflows/update.yml`** (line 42-45) — modern chains' branch:
    - Still runs `update --source node` to fetch the latest metadata, but produces no QR.
    - Runs `make collector` to refresh `data.json` digests.
    - Commits directly to `master` (no draft PR, no Matrix signing notification, no release manager). The verifier step remains as the safety net.
    - Legacy chains continue through the existing `sign-me-*` PR flow unchanged.

11. **`README.md`** — add a section explaining the two modes and the migration plan; remove the release-manager step *only* for chains in modern mode and call out which ones those are.

### Phase 2 — flip remaining chains

Because P1 verification already confirms every chain in `config.toml` has `CheckMetadataHash`, this phase is mostly mechanical: flip the per-chain `mode` flag from `legacy` to `modern` once Phase 1's UAT and stability are good, batch-roll the relay-chain parachains together (Asset Hub / Bridge Hub / Collectives / Coretime / People), and watch the deploy. No new code beyond Phase 1.

### Phase 3 — deprecate legacy

- When Vault v7+ adoption is broad enough (per P3) and all chains in `config.toml` are in modern mode, remove the legacy code paths: the entire `cli/src/signer/` module, the OpenCV camera dependency, the `Sign` subcommand, the `verifier` config block requirement.
- Update README to remove the release-manager steps.
- Bump major version, announce.

## What this gets us

- The release-manager step in the README ("Release manager … runs `make signer` locally to sign new metadata using his signing air-gapped device") disappears for all in-mode chains.
- The CI workflow `update.yml` becomes "fetch latest WASM, compute digest, commit, deploy" — fully automated, no human signature.
- We retain the original air-gap security guarantee through a stronger mechanism: instead of trusting an offline-held key, we trust the runtime's own digest (which was already in the trust root for any user signing a transaction).
- We *lose* the OpenCV / webcam / clang dependency tree on macOS, which is good.

## Verification plan

End-to-end checks after Phase 1:

1. `cargo test --release -p metadata-cli` plus a new test in `cli/src/digest/` that hashes a known WASM fixture and asserts the digest matches a value computed by an independent tool (e.g., `polkadart`'s metadata-hash example, or the runtime's baked `RUNTIME_METADATA_HASH` constant).
2. Cross-check: query the live Kusama runtime's baked digest (when a node-side RPC for it lands; until then, recompute from the WASM we used and compare to a release-time announcement on the Polkadot forum).
3. Live signing test: build a Kusama transaction in Nova Wallet → sign in Polkadot Vault v7+ using only the proofs Nova Wallet provides → submit. Should succeed without any metadata-portal QR being scanned beforehand. (This is the manual UAT for Phase 1.)
4. Frontend smoke: run `yarn start` after `make collector` and confirm the "modern mode" rendering for Kusama and "legacy mode" for an unmigrated chain.
5. Backwards-compat: a user on Vault < v7 signing on a chain still in `legacy` mode should see no behavioral change.

## Risks & open questions

- **P2 is the load-bearing remaining assumption.** If Vault v7+ still requires pre-signed metadata QRs even when `CheckMetadataHash` is on (e.g., for display purposes on chains the wallet didn't pre-fetch proofs for), then Phase 1 collapses to "publish digest in addition to the legacy signed QR" and we still can't drop the manual ritual. We must resolve P2 before merging the workflow change in step 10.
- **No node RPC currently exposes the runtime's baked digest.** We compute offline from the WASM via `merkleized-metadata`. If our computation ever disagrees with what's on-chain, we ship broken UI; mitigation is the single well-tested `cli/src/digest` module plus a runtime-API check when one lands.
- **Future chain additions** must be checked against P1 before being added in `modern` mode. The CI-time re-assertion in Phase 0 protects this — a `legacy`-mode default keeps additions safe.
- **Ethereum-named chains** in `config.toml` (none currently) would need separate treatment — RFC-0078 does not cover them in the same way.
